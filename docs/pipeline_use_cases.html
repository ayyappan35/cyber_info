A2A / Tool-Poisoning & LLM Defence — Pipeline Use Cases

How each request moves through the AI Security Gateway: evidence → skill routing → knowledge retrieval → LLM discussion → deterministic policy → MCP tool → verification.

Every request enters through security_gateway/gateway.py::analyze() with a fixed request_category and evidence the caller already computed (never the LLM's own claims). The Supervisor Agent picks which skill(s) under skills/<category>/ apply, a Security LLM Discussion reasons about the matched skills' guidance plus retrieved threat knowledge, and the final action is whatever the LLM proposed — clamped by policies/security_gateway_policy.yaml and any skill's deterministic floor/ceiling, neither of which the LLM can override.

Pipeline 1 — Agent-to-Agent (A2A) / Tool Poisoning

request_category = "agent_security" · entry point: backend/routers/agent_router.py · POST /api/agents/message

1. Evidence gathering

gather_agent_security_evidence() — looks up the real agent registry (agent_registry.py / security_db.registered_agents) for the sender's registered allowed_tools and role. Never trusts what the message itself claims.

▼

2. Supervisor Agent

route_agents() — agents/tool-abuse runs on every A2A message as the baseline check; agents/privilege-escalation is added only if the sender's role changed with no audited change event.

▼

3. Threat-knowledge retrieval

Query built from the matched skill id(s) (e.g. "tool abuse") against the security_threat_knowledge Chroma collection (seeded only from knowledge/cyber_defence/*.md) — similarity search, reranked, top‑4 chunks.

▼

4. Security LLM Discussion

Proposes action / confidence / reasoning / required_tools from the matched skill(s)' guidance + retrieved knowledge — a Pydantic-validated SecurityDecision, rejected outright if malformed.

▼

5. Deterministic floor (cannot be overridden)

tool-abuse/detection.yaml: if the requested tool isn't in the sender's registered set, the floor forces BLOCK — regardless of what the LLM proposed or how confident it was. The registry is the source of truth, not the message.

▼

6. Effect + MCP tool authorization

BLOCK → effect refuse_and_sandbox: message content quarantined as evidence, tool never executes. The LLM may additionally propose revoke_agent_credentials / remove_agent_tool_access — both requires_approval=True, queued for an admin.

▼

7. Verification + audit

_verify() re-reads real state (sandbox record exists?) before anything is reported successful. Logged to SIEM with decision_id; feeds chain_detection for multi-step attack correlation.

Pipeline 2 — LLM Defence (Prompt Injection / Jailbreak / RAG)

request_category = "rag_security" · entry point: chat pipeline (backend/pipelines/chat_agent.py) · POST /api/chat

1. Evidence gathering

gather_chat_evidence() — deterministic regex signals over the question (override / extraction / PII-request language) and the retrieved context (imperative / instruction-shaped language, PII patterns) separately.

▼

2. Supervisor Agent

route_chat() — llm/prompt-injection and rag/rag-poisoning are the default skills, always included as a baseline on every message; jailbreak, model-extraction, pii-exposure, external-api-abuse are added only when their own specific pattern hits.

▼

3. Threat-knowledge retrieval

Query built from the matched skill ids (e.g. "prompt injection rag poisoning") against the same security_threat_knowledge collection — top‑4 reranked chunks ground the discussion in MITRE ATLAS / prompt-injection reference material.

▼

4. Security LLM Discussion

Reasons about the question + retrieved context against every matched skill's guidance at once; returns action / confidence / reasoning / required_tools. reasoning is shown to the user directly, so it's constrained to plain language with no internal names.

▼

5. Deterministic floor / ceiling + policy clamp

Only fires when a skill's own narrow regex matched (e.g. jailbreak's "you are now", model-extraction's "reveal your system prompt"). Otherwise there is no floor — the baseline skills still ran, but the action is entirely the LLM's contextual judgment, then clamped to min_confidence_to_enforce = 0.5.

▼

6. Effect + MCP tool authorization

BLOCK → refuse_and_sandbox (fixed refusal, no context leaves the gateway); MITIGATE → sandbox_and_continue (answer still returned, evidence sandboxed); pii-exposure's own BLOCK instead queues disclose_pii_answer for admin approval.

▼

7. Verification + audit

Same _verify() + SIEM logging as Pipeline 1 — the Security LLM Discussion's own reasoning becomes the block message the user sees, not a generic refusal string.

Why none of these hit a deterministic floor: the regex lists in skills/llm/jailbreak/detection.yaml and skills/llm/model-extraction/detection.yaml are intentionally narrow (e.g. "ignore (all|any)?\s*(previous|prior|above)?\s*instructions" requires the word "instructions" to follow directly — "ignore all previous security instructions" doesn't match because of the extra word). That's by design, not a bug: CLAUDE.md explicitly forbids a giant hardcoded attack-signature if/elif chain. The baseline skills (prompt-injection, rag-poisoning) still run on every message regardless, and the Security LLM Discussion — grounded in the retrieved threat knowledge — is what actually catches paraphrased attacks the regex misses. A floor only exists for the highest-confidence, lowest-false-positive signatures; everything else is deliberately left to LLM judgment, then bounded by the policy's confidence threshold.
