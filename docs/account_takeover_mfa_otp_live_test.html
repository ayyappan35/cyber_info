Step 2MFA activates — require_mfa fires, real OTP emailed

This is the part that changed since the four-skill report: require_mfa no longer just flips a bit an admin has to clear. It generates a real 6-digit code, hashes it (bcrypt) into webapp_db.app_users.mfa_otp_hash with a 10-minute expiry, and emails it — real SMTP if SMTP_HOST is configured, otherwise the local outbox this run actually used.

Step 4OTP verification — wrong code rejected, correct code accepted

POST /api/auth/verify-otp checks the submitted code against the bcrypt hash stored against the account, with a 5-attempt / 5-minute rate limit (reusing redis_tool's existing block-identity mechanism) against brute-forcing the 6-digit space.

What changed vs. the original design: docs/login_auth_skills_live_test.html's account-takeover run ended at require_mfa setting an admin-clearable hold — "not a fake MFA challenge," but also a dead end for the account owner (403 forever, until an admin manually intervenes). This run exercises the replacement: a real one-time code, really emailed (SMTP when configured, an honest inspectable local outbox otherwise — never a fake/no-op send per CLAUDE.md Rule 3), that the owner clears themselves via POST /api/auth/verify-otp. The admin override (POST /api/admin/users/{username}/clear-mfa-hold) still exists as a fallback for a user who can't reach their registered email — see skills/authentication/account-takeover/SKILL.md's "MCP Tools" section.
