SetupMethodology & a real environmental quirk worth stating

Each of the 8 scenarios below was run against a freshly restarted server, one at a time, with every block cleared beforehand. That wasn't optional: redis_tool.py's sliding-window attempt counters live in-process and are keyed by source IP - running all 8 scenarios back-to-back against the same server (as a first pass here actually did) let earlier scenarios' attempt counts bleed into later ones (all scenarios originate from the same dev machine), making every later scenario look like an escalating multi-technique attack instead of 8 isolated signals. A real, honest artifact of how this design behaves under sustained pressure - and the reason each scenario below started from a clean process.

Two scenarios needed a specific real technique, not a shortcut: impossible-travel used two genuinely distinct loopback source addresses (127.0.0.1 and 127.0.0.2 - both real TCP peer addresses this dev machine can bind to, not a spoofed header the app doesn't even read) so request.client.host really differed between two logins on the same account. mfa-fatigue can only ever fire on an account already under an MFA hold, and account-takeover's own trigger is itself a non-deterministic LLM judgment call (see that section) - so its hold was established by calling require_mfa directly, the same real code path the LLM would have executed, before letting the LLM discussion run live on the resulting re-challenge pattern.

On non-determinism: every verdict above is a live, independent Security LLM Discussion call - the same evidence shape given a second time can score differently (documented at length for account-takeover in docs/account_takeover_mfa_otp_live_test.html, where the identical 3-fail-then-succeed pattern scored ALLOW twice before firing here). Nothing in this report should be read as "this exact input always produces this exact verdict" - only as "this is a real, captured example of the Security LLM reasoning correctly about this evidence shape."
What "unfiltered" means here: every scenario above was offered the identical 8-skill set - security_gateway/skills.py's CATEGORY_SKILLS["authentication"] now lists all 8, and supervisor_agent.py::all_skills_for() is pure enumeration - nothing about which account, IP, or evidence field was present changed which skills reached the prompt. Which skill(s) actually explain a verdict is reported back by the model itself (matched_skill_ids), not decided beforehand by regex routing. Tool arguments are the model's own too - grounded correctly in every run above, but see docs/AGENTIC_SYSTEM_EXPERIMENT.md for the risk that stops being true under a crafted, adversarial prompt rather than an ordinary attack pattern like these eight.
