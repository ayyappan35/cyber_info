Login authentication skills — detection & policy reference

Not a live-run walkthrough (that's docs/login_auth_skills_live_test.html) — this page is the source-of-truth reference: what detection.yaml declares per skill, what policies/security_gateway_policy.yaml enforces per category, and what each skill's own response.yaml overrides. Per CLAUDE.md section 7's distinction: SKILL = how to investigate, POLICY = what's permitted, LLM = reasons about context, MCP = executes the authorized action. The four files below are what actually get read by security_gateway/detection.py and security_gateway/policy.py — every value quoted here is copied verbatim from the real files, not paraphrased.

RefThe four layers, and where each skill's rules actually live

1 · detectskills/authentication/<skill>/detection.yaml

signals — the evidence fields this skill cares about. routing — now inert (see docs/login_auth_skills_live_test.html's standing correction: every skill is always offered to the Security LLM regardless, so this never actually filters anything today). floor — the one part that's still live code: detection.py::apply_floor(), called from gateway.py::analyze() after the Security LLM's own verdict (the model is always asked first, regardless of how unambiguous the evidence already looks — an earlier pre-emptive fast path that skipped the model call entirely for a hard floor hit was tried and then deliberately removed, so the model always gets a chance to reason), then raises the action to a guaranteed minimum whenever evidence alone matches — the LLM cannot talk this back down.

2 · policy (category default)policies/security_gateway_policy.yaml

One config block per request_category (authentication, rag_security, file_security, agent_security) — actions.<ACTION>.enabled and min_confidence_to_enforce, read by policy.py::clamp_action(), plus each action's effect (what actually happens — redis_block, log_only, ...) and config values like block_ttl_seconds, read by policy.py::action_effect()/action_config_value(). Applies to every skill in the category unless a skill's own response.yaml overrides it.

3 · policy (skill override)skills/authentication/<skill>/response.yaml

Optional, skill-specific. overrides.<ACTION> can change that action's effect or any config value just for this one skill — e.g. credential-stuffing/password-spraying's longer block_ttl_seconds, or account-takeover's MITIGATE getting sandboxed instead of just logged. Falls back to layer 2's category default for anything not overridden.

4 · enforcementsecurity_gateway/mcp_gateway.py + gateway.py's effect handling

The resolved effect from layers 2/3 drives what actually happens: redis_block → redis_tool.block_identity() (always the username, automatic on every BLOCK — see login_auth_skills_live_test.html's "IP block vs. username block"), sandbox_and_continue/log_only → quarantine or just a SIEM line, and any LLM-proposed tool (block_ip, rate_limit_user, ...) goes through mcp_gateway.py's own category-scope/rate-limit/requires_approval gate independently.

Skill 1brute-force

1 account, many passwords. The default/fallback skill for the category — no routing rule of its own, matched only when nothing more specific applies.

detection.yaml

skill_id: brute-force
category: authentication
default: true   # fallback when neither credential-stuffing nor account-takeover's routing rule matches

# No routing rule - this skill is the default/fallback for the category.

floor:
  field: recent_attempt_count_1min
  op: gte
  value: 5
  minimum_action: BLOCK
  reason: "5+ attempts against one account in a single minute is unambiguous - never left to model judgment alone."

policy.yaml (category default, authentication)

  BLOCK:
    enabled: true
    effect: redis_block       # identity added to the Redis/local block list
    block_ttl_seconds: 900

response.yaml override

overrides:
  BLOCK:
    block_ttl_seconds: 900   # restates the category default explicitly, no actual change

No real override here — 15 minutes is both the category default and this skill's own stated value.

Skill 2credential-stuffing

1 IP, many accounts, each its own password.

detection.yaml

routing:
  - field: distinct_usernames_from_source_5min
    op: gte
    value: 3
    reason: "3+ distinct accounts from one source in 5 minutes is a spray pattern, not single-account brute force."

floor:
  field: distinct_usernames_from_source_5min
  op: gte
  value: 10
  minimum_action: BLOCK
  reason: "10+ distinct accounts from one source has essentially no innocent explanation."

policy.yaml (category default) — same as brute-force above (one authentication block covers all four)

response.yaml override

overrides:
  BLOCK:
    block_ttl_seconds: 1800   # 30 min - longer than brute-force's 15, a spraying source is more likely automated/persistent

Skill 3account-takeover

≥3 failures → success, same account. The one skill of the four with no floor — a deliberate design choice, not an omission.

detection.yaml

routing:
  - field: this_attempt_success
    op: eq
    value: true
    and:
      field: failed_attempts
      op: gte
      value: 3
    reason: "A success immediately after 3+ recent failures on the SAME account is the takeover signature, not ordinary typo-correction."

# No floor - see SKILL.md's "what security boundaries apply" for why this
# is a deliberate choice, not an omission. Whether this fires is entirely
# the model's call - see the two real, opposite live outcomes for this
# exact evidence shape in login_auth_skills_live_test.html.

policy.yaml (category default)

  MITIGATE:
    enabled: true
    effect: log_only          # flagged in SIEM, login still proceeds on correct password

response.yaml override — the one real behavioral difference on this page

overrides:
  MITIGATE:
    effect: sandbox_and_continue   # unlike brute-force/credential-stuffing's plain log_only - this success needs a reviewable record, not just a log line

This is the only place any of the four skills actually overrides its category's effect (not just a config value like TTL): a MITIGATE account-takeover verdict genuinely writes a sandbox_items row (the message/evidence quarantined for review) even though the login itself still succeeds — brute-force and credential-stuffing's own MITIGATE never does that, they only log.

Skill 4password-spraying

1 IP, same password, many accounts. Its own floor sits lower than credential-stuffing's — same-password-across-accounts is judged a stronger signal than distinct accounts alone.

detection.yaml

routing:
  - field: distinct_usernames_same_password_5min
    op: gte
    value: 2
    reason: "Even 2 distinct accounts sharing an identical submitted password from one source is worth discussing - real users essentially never coincide on this."

floor:
  field: distinct_usernames_same_password_5min
  op: gte
  value: 5
  minimum_action: BLOCK
  reason: "5+ distinct accounts sharing an identical submitted password has essentially no innocent explanation - a lower bar than credential-stuffing's 10."

policy.yaml (category default) — same as brute-force above

response.yaml override

overrides:
  BLOCK:
    block_ttl_seconds: 1800   # matches credential-stuffing's - a spraying source is more likely automated/persistent
